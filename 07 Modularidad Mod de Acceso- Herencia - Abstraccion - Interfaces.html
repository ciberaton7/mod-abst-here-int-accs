1. Modularidad

El arte de dividir y organizar el código

El problema del código "Espagueti"

Cuando comenzamos a programar en primer semestre, es común escribir todo el código en un solo archivo (el famoso Program.cs). Esto funciona para tareas pequeñas, pero es insostenible en el mundo real.

Imagina un videojuego moderno: si escribieras la lógica de movimiento del jugador, la inteligencia artificial de los enemigos y el sistema de guardado en un solo documento, tendrías decenas de miles de líneas. Encontrar un error sería como buscar una aguja en un pajar.

// Código caótico: Todo en el mismo lugar
class JuegoCompleto 
{
    public void MoverJugador() { ... }
    public void EnemigoAtaca() { ... }
    public void GuardarPartida() { ... }
    public void CargarGraficos() { ... }
    public void ReproducirMusica() { ... }
    // ... 5000 líneas más ...
}

¿Qué es la Modularidad?

Es el principio de dividir un sistema masivo en piezas lógicas más pequeñas, independientes y manejables. A estas piezas las llamamos módulos.

Analogía del Campus Universitario: UNIFRANZ no es un solo salón gigante donde todos hacen todo al mismo tiempo. Está dividida en módulos: el área de admisiones, la biblioteca, los laboratorios de sistemas, y las aulas teóricas. Si hay que pintar la biblioteca, el resto de la universidad sigue funcionando sin enterarse.

// El código se organiza en piezas independientes
// Módulo 1: Solo se encarga del jugador
class Jugador { ... }

// Módulo 2: Solo se encarga del audio
class MotorAudio { ... }

// Módulo 3: Solo se encarga de guardar
class SistemaGuardado { ... }

Estructura Sintáctica: namespace

En C#, creamos un módulo envolviendo nuestro código con la palabra reservada namespace (espacio de nombres).

Piensa en un namespace como una carpeta virtual. Todas las clases que pongas dentro de esas llaves pertenecen a esa categoría específica. Esto evita que clases con el mismo nombre choquen entre sí.

  • 🔥 No existe un botón mágico o una configuración especial en el menú llamada "Crear Namespace". Un namespace es pura y exclusivamente una palabra reservada en el texto del código.
  • 🔥 Para agregar un NAMESPACE puedes: (*)Agregar una clase (click derecho en el documento => agregar clase=>ponen nombre=> Visual Studio les generará automáticamente una plantilla. Por defecto, Visual Studio le pone al namespace el mismo nombre que tiene el proyecto (por ejemplo, si su proyecto se llama SistemaEstudiantil, dirá namespace SistemaEstudiantil).).
  • 🔥 Lo único que el estudiante debe hacer es borrar ese nombre por defecto y escribir tu instrucción, dejándolo exactamente como tú lo pusiste:

A nivel profesional, los namespaces suelen reflejar las carpetas físicas del proyecto.
  • 🔥 Como buena práctica en el explorador de Soluciones, pueden hacer clic derecho en el proyecto -> Agregar -> Nueva Carpeta
  • 🔥 Nombran la carpeta "Academico" o el nombre que quieren que tenga el namespace despues del punto (como en el ejemplo).
  • 🔥 Hacen clic derecho sobre esa carpeta -> Agregar -> Clase -> Materia.cs.
  • 🔥Al hacerlo así, Visual Studio es inteligente y escribirá automáticamente el código base con el namespace anidado correspondiente al nombre de la carpeta, ahorrándoles el trabajo de escribirlo a mano

// Creamos un espacio para todo lo relacionado al usuario
namespace SistemaVentas.Usuarios
{
    public class Cliente { ... }
    public class Administrador { ... }
}

// Otro espacio para el inventario
namespace SistemaVentas.Inventario
{
    public class Producto { ... }
}

Conectando Módulos: using

Si tu código está dividido en namespaces, ¿cómo hacemos que hablen entre ellos?

Utilizamos la directiva using en la parte superior del archivo. Esto le dice a C#: "Oye, en este archivo voy a necesitar utilizar las herramientas que guardaste en este otro módulo".

// Archivo: Program.cs

// Importamos los módulos que necesitamos
using SistemaVentas.Usuarios;
using SistemaVentas.Inventario;

class Program
{
    static void Main()
    {
        // Ahora el sistema reconoce estas clases
        Cliente c1 = new Cliente();
        Producto p1 = new Producto();
    }
}

2. Modificadores de Acceso

La seguridad de tus datos (Encapsulamiento)

¿Qué son los Modificadores?

En la programación orientada a objetos, no queremos que cualquier parte del sistema pueda cambiar los datos de otra parte de forma accidental o malintencionada.

Los modificadores de acceso son palabras clave que actúan como "candados". Definen quién tiene permiso para ver o modificar las variables y métodos de una clase.

A la práctica de proteger estos datos la llamamos Encapsulamiento.

// El peligro de dejar todo sin candado:
public class CuentaBancaria
{
    // ¡Cualquiera puede modificar esto desde afuera!
    public double Saldo; 
}

class Hack 
{
    static void Main() {
        CuentaBancaria miCuenta = new CuentaBancaria();
        // Robo cibernético o error humano:
        miCuenta.Saldo = -999999; 
    }
}

Analogía: Tu Perfil de Redes Sociales

Piensa en tu cuenta de Instagram o Facebook:

  • Público: Tu foto de perfil y tu nombre de usuario. Cualquier persona en internet puede verlos.
  • Privado: Tus mensajes directos y tu contraseña. Solo TÚ, desde adentro de tu cuenta, tienes acceso a ellos. Ningún otro usuario puede leerlos ni alterarlos directamente.

En el código, queremos que variables sensibles (como contraseñas, saldos o cálculos críticos) sean estrictamente privadas.

public class PerfilUsuario
{
    // Visible para todo el mundo
    public string NombreUsuario; 
    
    // Totalmente oculto, el sistema lo protege
    private string Contrasena; 
    private string MensajesPrivados;
}

Los 3 Modificadores Principales

En C# utilizamos estas palabras clave antes de declarar variables o métodos:

  1. public: Sin restricciones. Accesible desde cualquier archivo o clase.
  2. private: Oculto. Accesible solo desde adentro de las llaves {} de la clase donde se creó.
  3. protected: Un punto medio. Accesible en su propia clase y en clases que "hereden" de ella (veremos herencia en breve).
public class PersonajeDeJuego
{
    public string Nombre; // Todos ven su nombre
    
    private int saludActual; // Nadie puede bajarle vida directamente

    public void RecibirDano(int cantidad) 
    {
        // Este método SÍ puede alterar la variable privada
        // porque está adentro de la misma clase.
        saludActual = saludActual - cantidad;
    }
}

La Solución Elegante: Propiedades

En lenguajes antiguos, creábamos funciones "Get" y "Set" separadas para proteger datos. En C#, la forma moderna de encapsular es usando Propiedades.

Una propiedad expone una variable de forma controlada. Usamos el bloque get para definir qué pasa cuando alguien lee el dato, y el bloque set para validar la información antes de guardarla usando la palabra clave value.

public class CuentaBancaria
{
    // Variable privada real (respaldada)
    private double _saldo;

    // Propiedad pública que actúa como filtro
    public double Saldo 
    {
        get { return _saldo; }
        set 
        { 
            // 'value' es lo que el usuario intentó guardar
            if (value >= 0) {
                _saldo = value; // Lo permitimos
            } else {
                Console.WriteLine("Error: Saldo negativo.");
            }
        }
    }
}

3. Herencia

No repitas código: La Jerarquía de Clases

¿Qué es la Herencia?

En ingeniería de software existe una regla de oro llamada DRY (Don't Repeat Yourself - No te repitas).

La herencia nos permite crear una clase nueva basándose en una clase que ya existe. La nueva clase (Hija) "hereda" o absorbe todos los atributos y métodos de la clase base (Padre) de forma automática.

La herencia siempre define una relación estricta del tipo "ES UN".

// Sin herencia, repetiríamos código aburrido:

class Perro { 
    public string Nombre; // Repetido
    public int Edad;      // Repetido
    public void Ladrar() { }
}

class Gato { 
    public string Nombre; // Repetido
    public int Edad;      // Repetido
    public void Maullar() { }
}

Analogía: Clases en un Videojuego (RPG)

Imagina que estás programando un juego de rol. Todos los personajes en el juego tienen características básicas: Nombre, Puntos de Vida (HP) y la capacidad de moverse.

Un Guerrero ES UN personaje. Un Mago ES UN personaje. En lugar de escribir el código de movimiento y vida desde cero para ambos, creas una clase base Personaje. El Guerrero hereda eso y añade lo propio: usar escudo. El Mago hereda eso y añade lo propio: lanzar hechizos.

// Clase Padre (Base)
public class Personaje 
{
    public string Nombre;
    public int Vida;
    public void Caminar() { Console.WriteLine("Avanzando..."); }
}

// Clase Hija (Usa los dos puntos :)
public class Mago : Personaje 
{
    public int PuntosDeMana;
    public void LanzarHechizo() { Console.WriteLine("Fuego!"); }
}

Estructura Sintáctica

Para indicarle a C# que una clase hereda de otra, simplemente colocamos el símbolo de dos puntos : después del nombre de la clase hija, seguido del nombre de la clase padre.

Nota importante: En C#, una clase solo puede tener UN padre (herencia simple). No puedes heredar de dos clases distintas al mismo tiempo.

// Comprobando la herencia en el Main:

Mago miMago = new Mago();

// Asignamos propiedad del PADRE (Personaje)
miMago.Nombre = "Gandalf"; 
miMago.Vida = 100;

// Asignamos propiedad del HIJO (Mago)
miMago.PuntosDeMana = 500; 

// Usamos método del PADRE
miMago.Caminar(); 

// Usamos método del HIJO
miMago.LanzarHechizo();

El Reto de los Constructores (La palabra 'base')

¿Qué pasa si la clase padre es estricta y exige datos obligatorios al momento de nacer (mediante un constructor parametrizado)?

La clase hija está obligada a recibir esos datos también, y debe pasárselos hacia arriba al padre usando la palabra clave base.

public class Vehiculo
{
    public string Marca;
    // El padre exige la marca para existir
    public Vehiculo(string marcaV) { Marca = marcaV; }
}

public class Auto : Vehiculo
{
    public int Puertas;
    
    // El hijo recibe los dos datos, se guarda 'puertas'
    // y redirige 'marcaV' al padre usando : base()
    public Auto(string marcaV, int puertas) : base(marcaV)
    {
        Puertas = puertas;
    }
}

Sobreescritura (Polimorfismo Básico)

A veces, el hijo hereda un método del padre, pero necesita hacerlo a su manera. C# permite reescribir la lógica.

El padre debe dar permiso marcando su método como virtual. Luego, el hijo reescribe el método utilizando la palabra override.

public class Enemigo
{
    // Virtual: "Autorizo que mis hijos cambien esto"
    public virtual void Atacar() 
    { 
        Console.WriteLine("Golpe normal de 10 daño."); 
    }
}

public class Dragon : Enemigo
{
    // Override: "Yo lo haré a mi manera"
    public override void Atacar() 
    { 
        Console.WriteLine("Aliento de Fuego! 100 daño!"); 
    }
}

4. Abstracción

Definir el "QUÉ", delegar el "CÓMO"

¿Qué es la Abstracción?

Es un principio avanzado donde aislamos el comportamiento esencial de un objeto y creamos plantillas que obligan a seguir ciertas reglas, ocultando la complejidad técnica.

Analogía del Reproductor Multimedia: Imagina aplicaciones como Spotify o Netflix. Como usuario, tú presionas un botón abstracto llamado "Play". Sabes QUÉ hace ese botón (reproduce el medio). Pero no te importa CÓMO lo hace internamente (decodificación de MP3, streaming de MP4, buffer de video). La abstracción es darle al programador el botón "Play" y ocultarle la matemática.

// Una clase abstracta es una plantilla incompleta.
// ¡El compilador prohíbe instanciarla directamente!
public abstract class ReproductorMultimedia
{
    public int VolumenActual;
    public void SubirVolumen() { ... }
    
    // Método abstracto: Le decimos a los hijos QUÉ hacer,
    // pero los obligamos a ellos a programar el CÓMO.
    public abstract void Play(); 
}

Estructura Sintáctica

Usamos la palabra clave abstract antes de la clase y antes de los métodos vacíos.

Presta mucha atención: Un método abstracto no tiene cuerpo (no tiene llaves {}). Simplemente termina en punto y coma.

Cualquier clase hija que herede de esta plantilla, estará obligada a escribir el código de ese método usando override. Si no lo hace, saldrá un error rojo en el IDE y no compilará.

// Clase hija hereda de la plantilla abstracta
public class ReproductorAudio : ReproductorMultimedia
{
    // El IDE nos obliga a implementar el método Play()
    public override void Play()
    {
        Console.WriteLine("Decodificando archivo MP3...");
        Console.WriteLine("Enviando señal a altavoces...");
    }
}

Ejemplo Complejo: Sistema de Figuras

Un clásico en ingeniería. Estás programando un software de dibujo CAD. Sabes que absolutamente todas las figuras geométricas pueden calcular su área. Pero la matemática es totalmente diferente para cada una.

Usamos abstracción para garantizar que todas tengan el método, pero que cada una resuelva su propia matemática.

public abstract class Figura
{
    // Plantilla vacía
    public abstract double CalcularArea();
}

public class Cuadrado : Figura
{
    public double Lado = 5;
    public override double CalcularArea() {
        return Lado * Lado;
    }
}

public class Circulo : Figura
{
    public double Radio = 3;
    public override double CalcularArea() {
        return 3.1416 * (Radio * Radio);
    }
}

El Poder Real: Polimorfismo

¿Para qué nos sirve tanta abstracción? Para procesar datos en masa de manera inteligente.

Como Cuadrado y Círculo derivan de la clase abstracta Figura, podemos guardarlos todos en una misma lista de tipo Figura. Luego, con un bucle, le decimos a cada uno "Calcula tu área", y C# sabrá automáticamente qué matemática usar para cada forma.

// En el Main: Lista genérica del tipo base
List<Figura> misFiguras = new List<Figura>();

// Agregamos formas mezcladas
misFiguras.Add(new Cuadrado());
misFiguras.Add(new Circulo());

foreach(var forma in misFiguras)
{
    // Magia: Llama a la fórmula correcta de cada hijo
    Console.WriteLine( forma.CalcularArea() ); 
}

5. Interfaces

Contratos de Diseño Estrictos

La gran pregunta: Clase Abstracta vs Interfaz

Parecen lo mismo, pero son fundamentalmente distintas:

  • Clase Abstracta: Es una plantilla a medio terminar. SÍ PUEDE tener variables, constructores y métodos con código real, mezclados con métodos vacíos. Define una relación de Identidad ("Un perro ES UN animal").
  • Interfaz: Es un contrato de diseño 100% estricto. NO PUEDE tener variables, ni constructores, ni una sola línea de código real. Solo dicta firmas de métodos vacíos. Define una relación de Capacidad ("Un objeto PUEDE HACER esto").
// Una Clase Abstracta tiene estado (variables)
public abstract class Vehiculo {
    protected int combustible = 100;
    public abstract void Arrancar();
}

// Una Interfaz NO tiene estado, solo reglas
public interface IVolador {
    void Despegar();
    void Aterrizar();
}

Analogía: El Tomacorriente de Pared

Piensa en los enchufes eléctricos de la pared. Ese enchufe físico establece un contrato o estándar (2 clavijas, 220V en Bolivia).

A la red eléctrica no le importa si tú conectas un televisor, el cargador de un celular, o un microondas. Son objetos totalmente distintos, sin ninguna relación de herencia entre sí. Pero mientras sus cables cumplan con la interfaz física del enchufe, el sistema funcionará.

// Por convención en C#, las interfaces empiezan con 'I'
public interface IEnchufable
{
    // Todo en una interfaz es público por defecto.
    // No usamos public/private ni llaves {}.
    void ConectarCorriente();
    int ConsumoEnergia();
}

Estructura Sintáctica

Para "firmar" el contrato, una clase usa los dos puntos : (igual que en la herencia).

Al hacerlo, te comprometes legalmente en el código a desarrollar todos los métodos de la interfaz. Nota: Aquí NO se usa la palabra override, simplemente escribes el método público con el mismo nombre y firma.

// El Microondas firma el contrato IEnchufable
public class Microondas : IEnchufable
{
    // Obligado a programar esto:
    public void ConectarCorriente()
    {
        Console.WriteLine("Microondas encendido, listo para calentar.");
    }

    // Obligado a programar esto:
    public int ConsumoEnergia()
    {
        return 1200; // Watts
    }
}

¿Por qué son tan poderosas? (Múltiples Interfaces)

En C#, una clase sufre de "Herencia Simple", es decir, solo puede tener UN padre (una clase abstracta o normal). ¡Pero puede firmar MÚLTIPLES interfaces al mismo tiempo!

Imagina un Teléfono Celular. Es un Dispositivo Electrónico (Herencia), pero además puede conectarse a WiFi (Interfaz 1) y puede tomar fotografías (Interfaz 2).

// Herencia de 1 Padre + Firma de 2 Contratos (Interfaces)
public class Celular : DispositivoBase, IConexionWiFi, ICamara
{
    // 1. Absorbe código de DispositivoBase
    
    // 2. Implementa métodos obligatorios de IConexionWiFi
    public void BuscarRedes() { ... }
    
    // 3. Implementa métodos obligatorios de ICamara
    public void TomarFoto() { ... }
}
